Abstract 
VoxKit is an extensible desktop workbench that addresses a gap 
in available tools: n o desktop application integrates forced 
alignment and goodness of pronunciation analysis in a single 
pipeline, creating a barrier to adoption for speech researchers 
working with clinical populations. With VoxKit, r esearchers 
can register datasets, select and train alignment engines, 
generate and compare alignments, and compute phone-level 
goodness of pronunciation scores within a single interface. 
Index Terms : forced alignment, goodness  of pronunciation, 
speech science, software 
1. Introduction 
Segmental speech science analyses require known boundaries 
between phones. The process of f orced alignment determines 
these boundaries automatically  by mapping an orthographic 
transcription to phonological segments through an acoustic 
model that identifies the most likely  acoustic intervals for  a 
window. The result is a set of boundary annotations that can be 
used for downstream acoustic analyses of individual phones.  
One such downstream analysis is  goodness of pronunciation  
(GOP) [1]. GOP methods use automatic speech recognition 
acoustic models to score the compatibility between the acoustic 
features of a segment and the possible phoneme labels for that 
segment. Traditional GOP methods have used phoneme 
likelihoods P(acoustics | phoneme), which measure how well 
the acoustics fit a given phoneme . P honeme posteriors, 
P(phoneme | acoustics), can also be used as GOP scores [2].  
GOP scoring requires forced alignment to identify the target 
phoneme for each audio interval, yet no desktop application 
integrates both analyses in a single pipeline. This gap is a 
barrier to adoption for speech researchers working with clinical 
populations. VoxKit addresses this barrier by providing a 
desktop software pipeline from raw audio to GOP outputs.  
2. VoxKit Pipeline 
2.1. System Architecture 
VoxKit (Figure 1) is a cross-platform desktop application built 
with Python 3.11 and PyQt6. It comprises six modules: 
graphical user interface, engines, storage, config, analyzers, and 
services. The GUI provides three panels: a Pipeline panel for 
running processing steps , a Datasets panel for registering and 
browsing corpora, and a Models panel for managing alignment 
models. Background processing runs on QThread workers, 
keeping the interface responsive during alignment and 
transcription. VoxKit is distributed as a standalone executable, 
downloadable from https://voxkit-web.vercel.app/. 
VoxKit is built around three abstractions that allow researchers 
and developers to extend the application without modifying its 
core. The stacker abstraction supports adding new pipeline 
steps; the workflows described in Section 2 are implemented as 
stackers, and new ones can be added over time. The alignment 
engine abstraction provides a common interface for speech 
processing backends; new engines propagate automatically to 
the pipeline, interface, and internal utilities. The anal yzer 
abstraction supports custom metadata extraction and 
visualization. VoxKit also implements layered configurability, 
separating build-time and post -build settings to allow flexible 
adjustments to pipeline order and stacker inclusion. 
2.2. Alignment Engines 
VoxKit includes two alignment engines. One alignment engine 
wraps the Montreal Forced Aligner  (MFA) and supports 
acoustic model adaptation  [3]. A second alignment engine 
wraps wav2vec2-based Wav2TextGrid, and supports aligner 
training [4, 5]. Each alignment engine stores config and model 
files within the application. New alignment engines can be 
registered without modifying the GUI, supporting  future 
extensions of VoxKit.  
2.3. Dataset Registration and Management 
VoxKit expects speech datasets  to be organized in speaker 
subdirectories, facilitating speaker-adaptive and other 
aggregative processing.  Each speaker subdirectory requires  
audio files and plain-text .lab transcript files matching audio file 
base names, following the conventions of the Montreal Forced 
Aligner. Pre-existing manual alignments (i.e., Praat TextGrids  
[6]) can also be imported for comparison with forced  
alignments or for aligner training. Supported audio formats 
include WAV, FLAC, MP3, OGG, and M4A.

To register a dataset (Figure 2), researchers point VoxKit to a 
speaker-organized dataset directory; VoxKit writes a metadata 
record with the dataset name, description, and registration date. 
Registered datasets appear in the Datasets panel, where 
researchers can browse tabular and graphical summaries. Each 
alignment run is stored as a separate record linked to the source 
dataset, enabling comparison of outputs from different 
alignment engines or model configurations.

2.4. Train Aligners 
VoxKit supports optional aligner training, ideally with manual 
alignments, prior to generating forced alignments. Training can 
be done using any existing TextGrid alignments, but training is 
most suitable for manual alignments imported in a registered 
dataset. The MFA alignment engine supports acoustic model 
adaptation. The Wav2TextGrid alignment e ngine supports 
training a Wav2Vec2 -based acoustic model from the dataset . 
Trained models are stored within the application and are 
available for selection in the Generate Alignments step. 
2.5. Generate Alignments 
Forced alignment runs on a registered dataset using a 
researcher-selected alignment engine and model. The MFA 
alignment engine requires a pronunciation dictionary in 
addition to the acoustic model, defaulting to english_us_arpa. 
The Wav2TextGrid alignment engine uses a tokenizer to map 
orthographic transcripts to phoneme sequences. Alignment runs 
on a background thread. Completed alignments are stored as 
TextGrid files linked to the source dataset. 
2.6. View and Compare Alignments 
VoxKit includes a built-in alignment viewer displaying phone 
and word boundaries synchronized with audio playback, 
emulating Praat TextGrid interval tiers. Researchers select a 
dataset and an alignment record to view. The comparison view 
reports corpus-level alignment metrics across two alignment s, 
including phoneme counts, boundary overlap, overlap rate 
above a configurable threshold, and phoneme substitution 
patterns. Researchers can compare outputs from different 
alignment configurations, or compare  forced alignments 
against manual alignments . This allows researchers to inspect 
alignment quality distributions before GOP analysis (Figure 3).

2.7. Goodness of Pronunciation Scoring 
After forced alignment, VoxKit c omputes Acoustic Goodness 
scores from the aligned data using a Wav2Vec2-based acoustic 
model pretrained on 960 hours of adult LibriSpeech [7] speech 
data to compute frame-level phoneme classification over a 42-
phoneme inventory at 10 ms resolution. The model is a 
discriminative classifier. Its outputs are phoneme posterior 
probabilities, P(phoneme | acoustics),  referred to as Acoustic 
Goodness. Acoustic Goodness is therefore operationalized as 
the log posterior probability of the target phoneme given the 
observed acoustics. Acoustic Goodness scores are saved for 
downstream analysis via two CSV output files: one containing 
per-frame scores alongside positional and phoneme-type 
features, and one containing scores aggregated by phoneme 
occurrence, utterance, speaker, or phoneme type. These outputs 
support group-level analyses of phoneme accuracy, including 
applications to child speech and clinical populations. 
3. Conclusion 
VoxKit provides an extensible desktop pipeline from raw audio 
to forced alignment to acoustic goodness outputs. VoxKit 
targets speech researchers, including clinical researchers, who 
require integrated and reproducible forced alignment and GOP 
workflows without command line programming expertise.
